# Политика хранения кэша сообщений

Остаток MSG2-14 из [#24](https://github.com/haltia-de/messenger/issues/24):
кэш сообщений не вытесняется. fsync и повторное заполнение `known.json`
уже сделаны в [#79](https://github.com/haltia-de/messenger/pull/79). Эта
записка — результат [#86](https://github.com/haltia-de/messenger/issues/86):
формат и пределы роста, предлагаемая конечная политика, что нельзя трогать,
как мигрировать, и что покажет фикстура. **Ничего из этого не удаляет
кэш человека.** Вытеснение в программе появится только после оценки
архитектора и человека.

Проверено по дереву, совпадающему с `main`
[`9a1bab5a496c2c5b857a5dd72061d8afa2820d3b`](https://github.com/haltia-de/messenger/commit/9a1bab5a496c2c5b857a5dd72061d8afa2820d3b)
(2026-10-29, 2.9.7, PR #89 про остановку конвейера звонка; `MessageCache`
там не менялся). Живой профиль, планшет и аккаунты не открывались.

## 1. Что сейчас на диске

Две разные «домашние» области (XDG, не `~/…`):

| Путь | Константа | Что это |
| --- | --- | --- |
| `~/.local/share/haltia-messenger/` | `DATA` | свои данные аккаунта |
| `~/.cache/haltia-messenger/` | `PHOTOS` | кэш, который можно пересобрать с сервера |

MAX держит свои файлы прямо в `DATA`; другой мессенджер — в
`DATA/<account>/` (`Account.folder`). Кэш сообщений **общий**:
`MessageCache` один на `Backend`.

### 1.1. Кэш сообщений (`CHATS`)

`~/.cache/haltia-messenger/chats/`:

- MAX: `<id>.json` (`MessageCache._path`, числовой id, как `%d`: `101.json`,
  не `007.json`);
- другой мессенджер: `<prefix>/<остаток>.json` (Telegram: `tg/5.json` для
  `"tg:5"`, `tg/-100123.json` для канала);
- рядом `list.json` — последний список чатов (`LIST`), чтобы список
  открылся сразу. Это не файл сообщений.

Формат файла чата — JSON-массив словарей сообщения, по времени, старые
первые. Поля, как их кладёт `Account.message`: `id`, `chat`, `sender`,
`who`, `text`, `photos`, `time`, `mine`, `reactions`, `yours`, `media`,
`forwarded`, `call`, `reply`. Версии и обёртки нет.

`MessageCache._get` при не-списке, битом JSON или отсутствии файла
подставляет пустой список в память и **не** удаляет файл. Список
не-словарей или словарей без `id` `_get` так не отфильтровывает:
`read` (`dict(m)`) и `add` (`m["id"]`) на нём падают. Неизвестный
формат политика не вытесняет.

Пишется целиком, атомарно (`.new` + `os.replace`), режим 600, каталог 700.
Таймер 2 с после последнего изменения и `flush()` при выходе.
`MessageCache.flush` **не** делает `fsync`; `save_text` для файлов `DATA`
делает (это как раз часть MSG2-14 из #79, не эта задача). `os.replace`
ставит файлу **новое mtime** — это время последней записи, не открытия.

### 1.2. Уже ограничено

На один чат `add()` оставляет новейшие `KEEP` (80) сообщений. Это не
предел числа файлов и не предел байт.

Уже вытесняются, и это не кэш истории:

- фото `*.img` в `PHOTOS` — не показывались `PHOTO_DAYS` (30) суток,
  `Media.prune`, при старте и раз в день;
- документы в `DOCS` — последние `DOCS_KEPT` (30) папок, `prune_docs`;
- файлы из других программ в `SHARED` — старше суток.

`older()` страницы старше кэша **не** записывает: на диске только хвост.

### 1.3. Где рост не ограничен

Число файлов чатов. Файл появляется при `cache.add` (история, входящее,
отправка, пересылка) и живёт дальше. Снимается только:

- выход из аккаунта — `Backend.logout` вызывает `cache.drop` по ключам
  **`account.chats`**, не обходом каталога: файл чата, которого уже нет в
  списке, остаётся;
- удаление или выход из чата — `Account.remove` → `drop`;
- разрыв истории — `history` видит gap и `drop` этого чата, затем пишет
  новую порцию.

Чаты, которые пропали из списка после входа, свои файлы не теряют. Новых
сообщений в тихий чат всё равно пишет `on_message` → `add` → `flush`, то
есть **mtime файла — время входящей записи**, даже если человек чат не
открывал. Открытие (`read` / `history`) mtime сегодня не меняет.

Грубая оценка (не замер на планшете): порядка 0,5–2 КБ на сообщение, до
`KEEP` штук — десятки–сотни КБ на чат. Тысячи когда-либо открытых или
получивших сообщение чатов — десятки–сотни МБ одних JSON, без фото.
Это оценка, не потолок.

`list.json` растёт как список чатов (сводка на чат), не как история.

### 1.4. Свои данные — не кэш истории

Их политика вытеснения не касается.

| Где | Что | Владелец |
| --- | --- | --- |
| keyring / `DATA/<account>-session.json` | сессия | аккаунт |
| `DATA/known.json` или `DATA/<account>/known.json` | свои люди | аккаунт; пустой список — уже заполненный, битый — закрыт |
| `DATA/names.json` / `DATA/<account>/names.json` | свои имена | аккаунт |
| `DATA/chats.json` (`PREFS`) | закрепление и уведомления | общее, локальное |
| `DATA/emoji.json` | недавние эмодзи | общее |
| `~/.config/haltia/messenger.conf` | настройки | общее |

Неотправленное **на диск в кэш не попадает**:

- очередь `Max.queue`: id `"out-N"`, поле `state` (`sending` / `failed`),
  только в памяти процесса;
- черновики `Max.drafts`: текст и вложения открытого чата, тоже только в
  памяти.

Пока так, вытеснение файлов `CHATS` неотправленное не сотрёт. Политика всё
равно отличает такое сообщение, если оно когда-нибудь окажется в файле
(сейчас `add()` отрежет его вместе с хвостом, если оно старше `KEEP`
серверных).

## 2. Варианты

Общий предел нужен по **числу файлов** (не по байтам), не только `KEEP`
внутри файла. Число файлов — не потолок места: один файл до `KEEP`
сообщений, размер разный; защищённые, нечитаемые и чужие имена остаются
сверх числа.

**A. Только возраст** (`CHAT_DAYS`, как фото). Просто, но чат с регулярной
рассылкой никогда не устареет: `on_message` обновляет файл. Число файлов
при этом не ограничено.

**B. LRU по числу файлов и по штампу доступа** (`CHATS_KEPT`, как
`DOCS_KEPT`). Верх числа файлов есть всегда. Тихие **открывавшиеся** чаты
остаются, шумный канал без открытия — нет. Их снова откроет запрос
`PAGE`, если история ещё есть на сервере. **Это рекомендация.** LRU по
mtime записи для этого не годится: `flush` при входящем сам ставит новое
mtime, и канал, который никто не открывал, выглядит новее личной
переписки.

**C. Потолок байт.** Точнее по месту, хуже объясняется и проверяется.

**D. Отдельный потолок на аккаунт.** Справедливее при двух мессенджерах,
сложнее. Можно после B.

Возраст как добавка к B не обязателен: при живом потоке сообщений он не
режет как раз те файлы, которые растут.

## 3. Рекомендуемая политика

Пока только правило. Программа его не исполняет.

1. **Внутри чата.** Новейшие `KEEP` **серверных** сообщений, как сейчас.
   Сообщения только здешние (`id` вида `"out-…"` или `state` `sending` /
   `failed`) из этого хвоста не выкидывать. Сейчас `add()` их не отличает.
2. **Между чатами.** Не больше `CHATS_KEPT` **читаемых канонических**
   файлов (предложение: **200**). Среди незащищённых вытеснять целиком
   самые старые по **штампу доступа**, не по mtime записи. Штамп —
   соседний файл `<id>.accessed` (число Unix-времени). Его пишет только
   открытие чата человеком. Входящее `flush` его не создаёт и не
   двигает, хотя mtime JSON после `os.replace` новое. 200 × 80 × ~1 КБ —
   порядка единиц–десятков МБ JSON у незащищённых читаемых файлов; это
   оценка, не потолок байт.
3. **Не трогать файл**, если:
   - это `list.json`;
   - в массиве есть здешнее сообщение;
   - id чата передали как защищённый (открытый, закреплённый — в
     реализации);
   - JSON не читается, это не список, в списке не словари или нет `id`
     (неизвестный формат; не вытеснять «на всякий случай»);
   - соседний `.accessed` **есть**, но это не конечное число (мусор,
     пустой файл, NaN, ±Infinity): неизвестные метаданные. Чат
     пропускается, как нечитаемый JSON. Отсутствующий штамп — другое:
     «не открывали», его можно вытеснить;
   - имя не каноническое (`007.json`, `+5.json`, `1_0.json`) или префикс
     каталога не из известных (`tg` — Telegram; MAX — числовой `.json` в
     корне `CHATS`). Чужой префикс и такое имя **не вытесняются**.
4. Защищённые, нечитаемые и чаты с битым штампом могут превысить
   `CHATS_KEPT`. Тогда вытесняется только незащищённое читаемое с
   годным штампом (нет файла или конечное число), пока есть что
   вытеснять. Пропущенные в потолок не входят и остаются навсегда, пока
   их не починят; после прохода в каталоге может быть больше
   `CHATS_KEPT` файлов. Фикстура это считает (`skipped_count`,
   `over_cap`).
5. Один проход по всему `CHATS` (MAX и `tg/` вместе): место общее.
   Владение видно по пути: канонический числовой `.json` — MAX,
   `tg/<канонический id>.json` — Telegram. Обход не ходит в `DATA`, не
   следует по симлинкам и не путает файлы. Новый мессенджер не попадает
   под вытеснение, пока его префикс не добавят в белый список.
6. Вытеснять **файл целиком**, не переписывая массив (кроме уже существующего
   `KEEP` в `add()`). Полузаписанные `.new` этот проход не трогает: они
   остаются, фикстура их считает, предела нет. Сиротские `.accessed`
   (нет соседнего JSON) этот проход тоже не подметает: считает
   (`orphan_stamp_count`) и оставляет. Это ограничение, не баг правила.
   Соседний `.accessed` уходит вместе с JSON, **если проход удаляет
   этот JSON**.
7. **Штамп доступа, не mtime.** Реализация (не здесь) при открытии чата
   (`read` / `history` с экрана) пишет `.accessed`. Входящее сообщение
   этого не делает. Трогать mtime при открытии **недостаточно**: каждый
   `flush` его перезаписывает, и шумный канал без открытия всегда новее
   тихой личной переписки, которую открыли на прошлой неделе.
   `MessageCache.add` / `flush` штамп не создают и не двигают; фикстура
   это проверяет настоящим `add`/`flush`, не подставной переписью JSON.

Миграция штампа: файла `.accessed` **нет** — чат **никогда не открывали**
после введения политики (значение «нет штампа», в ранжировании раньше
любого конечного числа). Старое mtime для этого **не подставлять**: оно
как раз время записи. Файл **есть**, но прочитать конечное число нельзя —
чат пропускают, как неизвестный формат, и **не** считают «не
открывали»: иначе открытый чат с битым штампом проиграл бы никогда не
открытому. Следствие: до первого открытия человеком все нынешние файлы
без штампа равны по доступу; среди них порядок — mtime, затем id.
Первый проход после включения ещё может удержать шумный канал вместо
тихой переписки, которую открывали до штампов. После того как человек
открыл тихий чат, повторные входящие в канал его не вытесняют. Фикстура
это показывает.

Штамп — **стенные часы** Unix (`time.time()` в реализации). Отдельного
счётчика или монотонных часов эта задача не вводит. Планшет с часами в
1970 запишет почти ноль и чат станет самым старым, пока его снова не
откроют уже с верными часами; часы в далёком будущем сделают чат новее
всех, пока то же самое. Скачок NTP — тот же класс слабости, что у
ранжирования по mtime, только теперь на нём весь порядок. Запись штампа
на каждое открытие **без троттлинга**: маленький файл режима 600, одна
запись на eMMC за открытие, не через таймер `flush`. Стоимость надо
назвать в реализации; новый глобальный таймер сюда не добавляем.

Неотправленное и черновики по-прежнему не обязаны жить в этом кэше. Если
их начнут писать на диск, формат — тот же массив с `"out-…"` / `state`, и
пункт 3 их сохранит. Пока процесс умер — очередь и черновик пропадают;
это отдельный разговор, не MSG2-14.

История на сервере **не обещана**. Вытесненный файл при следующем
открытии запросит `PAGE`. Сервер может уже не отдать ту же историю
(чат удалили, сессия кончилась, сервис забыл). Поэтому здешние
сообщения защищены, а «можно снова скачать» — не гарантия.

### 3.8. Жизнь штампа рядом с `drop`

Сегодня `MessageCache.drop` снимает только JSON. Его вызывают:

- разрыв истории — `Account.history` видит gap и `drop`, затем `add`
  новой порции того же id;
- удаление или выход из чата — `Account.remove` → `drop`;
- выход из аккаунта — `Backend.logout` обходит **`account.chats`** и
  `drop` каждого, не каталог.

Штамп после этого остаётся сиротой. Проход вытеснения его считает и
**намеренно не подметает** (как хвосты `.new`). Предела числу сирот нет.

Если тот же id снова получит JSON (gap переписал кэш, вышли и
вернулись в канал, заново вошли в аккаунт и чат появился), старый штамп
снова сосед и **засчитывается как доступ**. Это может удержать
воссозданный чат или, наоборот, вытеснить его по давней дате. Пока
`drop` в программе штамп не трогает; это не меняется в этой задаче.
Реализация, которая включит вытеснение, должна снимать `.accessed` вместе
с JSON в `drop` (или явно принять наследование). Фикстура: настоящий
`drop` оставляет сироту; `apply_plan` при вытеснении штампованного чата
снимает и JSON, и `.accessed`.

## 4. Миграция

Формат JSON не меняется: тот же массив. Обход при старте смотрит текущие
файлы и удаляет только то, что правило разрешило. Переписывать JSON,
ставить версию, трогать `DATA`, сессии, `known.json`, `names.json`,
`chats.json` не нужно. Штамп доступа — новый соседний файл; его нет у
старых чатов, и это как раз значение «не открывали».

`_get` уже считает не-список пустым кэшем. Обёртка `{version, messages}`
без правки чтения стала бы пустым кэшем; поэтому её не вводить, пока
чтение не умеет оба вида, и в этом PR её нет. Список без `id` чтение
сегодня не считает пустым — падает; такие файлы проход не удаляет.

`logout` сегодня не подбирает файлы, которых нет в `account.chats`, и
`drop` не снимает `.accessed` (см. 3.8). В реализации вытеснения: либо
обход по префиксу аккаунта, либо общий `CHATS_KEPT` их когда-нибудь
снимет как давно не открывавшиеся; `drop` должен снимать штамп вместе с
JSON. Пока ничего не удалять «на выходе» сверх нынешнего `drop`.

Старые профили: первый проход может снять много файлов без штампа
доступа. Это может быть необратимо, если сервер историю не отдаст.
Поэтому до явного согласия на реализацию ничего не удалять. Закреплённые
и чат на экране защищать с первого дня включения.

## 5. Фикстура

`tests/cache_retention_fixture.py` и `tests/test_cache_retention.py`.
Каталог только временный (`common.load` подменяет `HOME` / XDG). Настоящий
профиль не читается и не пишется. `own_scratch` сам принимает только путь
во временном каталоге процесса и не создаёт никакой другой; `apply_plan`
принимает только корень, который фикстура пометила; путь снаружи, симлинк
и чужой каталог отвергаются целиком, ничего не удаляется. Это не общая
песочница, только страж удаления фикстуры.

Фикстура:

- пишет файлы тем же `MessageCache`, что и программа, плюс один чат с
  `"out-1"`;
- ставит детерминированные mtime, где нужен порядок среди неоткрытых;
  штамп доступа — соседний файл, не подмена mtime;
- сцена доступа: входящие в канал и дописка в тихий чат идут через
  настоящие `MessageCache.add` / `flush`; штамп после них тот же;
- кладёт `list.json` в `CHATS` и `known.json` плюс ложный `999.json`
  **в `DATA` вне** обхода; обход **родителя** (где и `data/`, и `chats/`
  — чужие префиксы) их не видит;
- считает план при `keep=3` и применяет его только к этой песочнице;
- отдельно: защищённые больше `keep` (точный набор вытеснения),
  нечитаемая форма, чужие префиксы и неканонические id, отказ
  `apply_plan` и `own_scratch` вне временного каталога, битый/NaN/Inf штамп (пропуск,
  точные kept/evicted/skipped/over_cap), сирота после настоящего
  `drop` и снятие штампа при вытеснении штампованного чата.

Ожидание при шести файлах чатов без штампов: вытеснить три самых старых
по mtime **без** здешнего сообщения; оставить недавние MAX и Telegram и
чат с `"out-1"`; `list.json`, `known.json`, ложный файл в `DATA` и
хвост `.new` на месте. Сцена доступа: тихий чат со штампом 50 и старым
mtime, канал без штампа с mtime после трёх входящих `add`/`flush` — при
`keep=1` остаётся тихий, штамп не сдвинулся. Битый штамп при `keep=1`:
чат со штампом 50 остаётся, чат без штампа уходит, четыре с мусором /
NaN / ±Inf пропускаются, `files_before=2`, `files_after=1`,
`skipped_count=4`, `over_cap` истинно. Тем же прогоном видно, что
нынешний `add()` уже отрезает старое `"out-…"` при переполнении `KEEP`
— поэтому пункт 1 политики нужен до включения вытеснения файлов, если
неотправленное начнут кэшировать.

## 6. Что делать в реализации (не этот PR)

После принятия политики:

1. Константа `CHATS_KEPT`, чистые `plan_cache_eviction` / `is_local_message`
   / `canonical_int_stem` (уже в фикстуре) перенести к `MessageCache`.
2. `MessageCache.prune(keep, protect_ids)` — только по плану, только в
   **своём** каталоге этого экземпляра; вызывать со `CHATS` при старте.
   Этого вызова в программе сейчас нет.
3. `add()`: здешние сообщения не входят в обрезку `KEEP`.
4. Открытие чата пишет штамп доступа (стенные часы, конечное Unix-время;
   NaN/Inf не писать). Одна запись на открытие, без троттлинга; стоимость
   на eMMC назвать. `flush` штамп не трогает и **не** подменяет его
   mtime. mtime остаётся временем записи. Новый глобальный счётчик или
   часы не вводить.
5. `protect_ids`: открытый чат, закреплённые из `ChatList.pinned`.
6. `drop` (gap, `Account.remove`, `logout` по `account.chats`) снимает
   `.accessed` вместе с JSON, чтобы воссозданный id не наследовал доступ.
   Сирот, которые уже лежат, этот первый prune может оставить: предела
   нет, это надо сказать. По желанию: `logout` обходит файлы своего
   префикса.
7. Тесты на настоящий `prune`, без удаления чужого `HOME`.

Потолок, гонки и память — **ограничения follow-up, не поведение этой
ветки**. Пока их нет в коде, вытеснение включать нельзя:

- Держать `MessageCache.lock` на время решения и снятия из памяти.
  Для каждого вытесняемого id: как в `drop` — убрать `self.chats[id]`,
  выкинуть из `dirty`, поднять `self.gen[id]`. Иначе следующий
  `_changed` снова запишет файл.
- Учесть одновременный `flush`: он снимает снимок, пишет `.new`, под
  замком проверяет `gen` и только тогда делает `os.replace`. Если
  prune снимет JSON, не подняв `gen`, `replace` вернёт файл (воскрешение).
  Если `flush` уже сделал `replace` после unlink — тоже. Порядок как у
  нынешнего `drop` против `flush`.
- Грязный чат в памяти и поколение записи — часть того же правила, не
  отдельный проход по диску.
- Хвосты `.new` можно оставить (фикстура так и делает) или снимать
  старые под тем же замком; пока предела нет, это надо сказать в
  реализации.
- Штамп и JSON не должны расходиться с тем, что в памяти: запись штампа
  при открытии — под замком или так, чтобы prune её видел.
- Присутствующий битый штамп — пропуск чата, не «никогда не открывали».

Не в этой задаче и не в том follow-up без отдельных issue: запись очереди
и черновиков на диск; потолок байт; отдельный потолок на аккаунт; выпуск;
аккаунты; планшет; issue #84, #85, #88.

## 7. Пределы этой проверки

- `main` закреплён по GitHub API, не по локальному git (у исполнителя копии
  без git).
- Размеры живого кэша на планшете не мерялись.
- Python/GI в песочнице исполнителя может не быть: приёмка тестов — у
  архитектора (`tests/run.sh`).
- Политика не включена: `MessageCache` по-прежнему не удаляет файлы чатов
  сам по себе. Фикстура удаляет только помеченное ею временное дерево.
- Потолок 200 — предложение, не одобренное удаление.
- Нечитаемые, защищённые и чаты с битым штампом могут оставить в
  каталоге больше 200 имён; число файлов — не потолок байт и не обещание,
  что сервер отдаст историю.
- История на сервере после вытеснения не гарантирована.
- Первый проход по профилю без штампов доступа ещё ранжирует неоткрытые
  файлы по mtime записи.
- Штамп зависит от стенных часов; скачок часов ломает порядок до
  следующего открытия. Сиротские штампы и `.new` копятся без предела.
  Нынешний `drop` штамп не снимает.
